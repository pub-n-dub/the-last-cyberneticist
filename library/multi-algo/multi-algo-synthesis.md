# Multi-algo synthesis: McAulay’s multenions and Trakhtenbrot’s algorithms

## Purpose

This note combines two project knowledge sources:

- [Trakhtenbrot knowledge notes](../algorithms/trakhtenbrot-algorithms-and-automatic-computing-machines-notes.md), based on *Algorithms and Automatic Computing Machines*.
- [McAulay knowledge notes](../multenions/mcaulay-multenions-and-differential-invariants-knowledge.md), based on *Multenions and Differential Invariants*.

The synthesis is deliberately narrow. It does **not** claim that McAulay supplied a modern programmable controller, or that Trakhtenbrot supplied a multenion algebra. It extracts a disciplined joint programme:

> An algebra specifies the objects and lawful transformations available at a moment; an algorithm specifies which lawful transformation occurs next, under which condition, with what stored state, termination rule, and evidence.

This is a design and research framework, not a claim that a hardware or GA144 implementation already exists.

## The two sources answer different questions

| Question | McAulay | Trakhtenbrot | Hybrid requirement |
| --- | --- | --- | --- |
| What kinds of objects exist? | Scalars, vectors, vectoriums, grade components, linities | Encoded data and machine configurations | Name the represented objects and their storage/encoding. |
| What operations are lawful? | Associative noncommutative product, grade projections, linities, rotations | Elementary machine instructions | Give each implemented operation a formal meaning and a machine procedure. |
| What happens next? | Not a program-selection theory | Conditions, jumps, loops, halt | State a deterministic transition rule. |
| What remains true during execution? | Algebraic identities, grade and sign rules | Invariants, configuration semantics | State and test electrical/program invariants that preserve the algebraic contract. |
| How is a result checked? | Scalar-part pairings, normal reciprocals, invariant forms | Trace, halt condition, reproducible run | Record inputs, states, chosen operation, result, and verification. |
| What are the limits? | Historical formalism; no supplied machine realization | Practical infeasibility and undecidability | State the finite machine’s scope; do not imply universality. |

## Non-negotiable historical and formal boundary

McAulay’s multenions are an **associative**, noncommutative, graded algebra. They are generated by `n` anticommuting primitive units with squares `−1`, and the general `n = 4` case has sixteen independent scalar components.

Therefore this hybrid must not conflate McAulay’s system with:

- an eight-component octonion system;
- a nonassociative product;
- a finite-state machine by itself; or
- a proof of Turing completeness, universal computation, or machine intelligence.

Associativity means that a correctly implemented McAulay product may be regrouped according to valid associative identities. **Order still matters:** in general, `uv ≠ vu`. An implementation must preserve operand order, grades, signs, and the source algebra’s stated projections.

## A two-layer model

```text
          McAulay: static algebraic layer
   basis · grade · product · projection · linity · invariant
                              │
                              │ representation and operation contract
                              ▼
      Trakhtenbrot: dynamic algorithmic layer
 input · state · condition · transition · memory · trace · halt/error
                              │
                              ▼
        physical/program implementation and test record
```

The top layer says what an operation *means*. The middle layer makes the correspondence explicit. The lower layer says when an operation is selected and how a run can be reconstructed.

Neither top nor bottom layer alone is sufficient:

- Algebra without a transition rule does not tell a machine what to do next.
- A transition table without formal operation semantics may be a working program but cannot establish that it realizes McAulay’s specific structure.

## The hybrid contract

Before calling a controller or program “multenion-informed,” complete all six parts of this contract.

### 1. Algebraic contract

Specify the exact finite fragment of McAulay’s algebra in use.

At minimum:

```text
coefficient domain:  ______________________________
dimension n:         ______________________________
basis order:         [1, i1, i2, …, products …]
included grades:      ______________________________
product rule:         ia² = −1; iaib = −ibia (a ≠ b)
projection(s):        Va for stated values of a
linity/operation:     ______________________________
identity to preserve: ______________________________
```

Do not write “Multenions” as a label where `n`, coefficient domain, basis convention, and enabled operations remain unspecified. In particular, a 16-component general `n = 4` representation and a chosen even subalgebra are different objects and need different contracts.

### 2. Representation contract

Map every formal object to an inspectable representation.

| Formal object | Required implementation declaration |
| --- | --- |
| scalar coefficient | integer, rational, fixed-point, floating point, or other domain; width and overflow/rounding rule |
| primitive unit | basis index, symbol, register code, or memory location |
| vectorium / grade component | coefficient layout and grade tag or fixed layout convention |
| product | exact routine, table, circuit, or micro-operation sequence |
| `Va` projection | selection/zeroing rule plus an example input/output |
| linity | input layout, output layout, and preserved relation |
| normal reciprocal / invariant pairing | test procedure and expected scalar result |

Trakhtenbrot’s lesson applies directly: representation is part of the procedure. A formal symbol that has no declared machine representation cannot yet participate in an executed algorithm.

### 3. Transition contract

State the algorithm that chooses the next lawful operation. A minimal controller needs:

| Element | Question it must answer |
| --- | --- |
| Initial state | Which represented objects are valid at the start? |
| Input condition | What new datum, event, or request is being read? |
| Relation/evaluation | What condition is computed from the present state? |
| Permitted transformation | Which named operation is selected for each condition? |
| Memory update | What changes, where is it written, and when is it valid? |
| Verification | How is the result read back or checked against an invariant? |
| Halt/error | What ends the cycle, and what happens when a precondition fails? |

The central separation is:

```text
algebraic relation ≠ policy choice ≠ state update ≠ verification
```

For example, an algebra may allow a product and a grade projection. It does not thereby choose whether a controller should multiply, project, store, retry, or halt. That choice belongs to the algorithm.

### 4. Invariant contract

Each implementation should name conditions that remain true across every permitted transition. Candidate invariants include:

- Every stored value has a declared basis and coefficient representation.
- A projection labelled `Va` contains only the declared grade-`a` component.
- An operation never silently swaps factors in a noncommutative product.
- A write occurs only after all required operands are valid.
- A failed representation or arithmetic precondition enters a named error state rather than producing an unlabelled result.
- A trace event is emitted for every state-changing operation.

McAulay supplies algebraic identities that can become test oracles. Trakhtenbrot supplies the proof pattern: state the invariant, show that every permitted step preserves it, and make the execution inspectable.

### 5. Evidence contract

For each run, preserve a minimal trace:

```text
run ID / program version
algebraic contract version
input coefficients and basis order
initial machine state
selected operation and operands in order
output coefficients and grade/projection
invariant or readback check
next state
halt or error reason
```

This turns a result from a display into evidence. A final value alone does not reveal whether the intended product, projection, ordering, or transition was actually used.

### 6. Scope contract

State what the system does **not** claim.

Examples:

- “This is a bounded arithmetic demonstrator for one stated multenion fragment.”
- “This is a finite-state controller, not a universal Turing machine.”
- “The trace verifies specified cases; it is not a proof of every algebraic identity.”
- “A general word-problem or equivalence result has not been established for this representation.”

This is not a rhetorical downgrade. It is the condition that makes the positive result credible.

## A minimal executable research cycle

The following abstract cycle is a safe bridge from the two sources. It is not yet a GA144/Forth/ROM implementation.

```text
State: IDLE
  receive a request containing an operation tag and well-formed operands
  → VALIDATE

State: VALIDATE
  check basis convention, grade/domain compatibility, and storage availability
  valid → EXECUTE
  invalid → ERROR

State: EXECUTE
  perform exactly one named algebraic operation in declared operand order
  → PROJECT_OR_STORE

State: PROJECT_OR_STORE
  apply a declared Va projection if the operation requires one
  write the result with its representation tag
  → VERIFY

State: VERIFY
  perform readback and/or a stated identity check
  pass → TRACE
  fail → ERROR

State: TRACE
  record operation, operands, result, check, and state transition
  → HALT or IDLE

State: ERROR
  record the violated precondition or failed check
  → HALT
```

This cycle implements Trakhtenbrot’s demand for determinate control while keeping McAulay’s operations explicit. It deliberately avoids the false move of treating the algebra’s multiplication rule as if it were already a behavioural policy.

## The labyrinth invariant: a model for inspectable search

Trakhtenbrot’s labyrinth algorithm is especially useful when the hybrid is asked to explore alternatives—such as possible rewrite paths, candidate transformations, test branches, or fault-isolation branches. It is stronger than a loose “feedback-loop” analogy because it includes a proved memory discipline.

It also extends the architectural vocabulary established in Episode 4. Activities, modes, transitions, and conditions describe the structure of possible conduct. The Ariadne thread adds a historical and evidential dimension: it records the route actually taken through that structure, including abandoned branches and stated limits. Architecture is therefore not only a diagram of what a system may do; in a legible machine it is a recoverable account of what it did.

### The source invariant

In the finite labyrinth, corridors are marked:

```text
green  = never traversed
yellow = traversed once; part of the active thread path
red    = traversed twice; closed to further traversal
```

At every step, the yellow corridors form one simple path from the start to the current position. The traveller never uses a red corridor. Since the labyrinth is finite and every corridor is traversed at most twice, the procedure eventually stops: either it finds the target or it returns to the start after exhausting the reachable region.

The original procedure permits a choice among green corridors; Trakhtenbrot converts it into a genuine deterministic algorithm by requiring a fixed choice convention.

### Hybrid correspondence

| Labyrinth term | Hybrid search meaning | Required evidence |
| --- | --- | --- |
| junction | a complete controller/search configuration | state identifier plus relevant represented multenion data |
| corridor | one permitted, named transition | operation name, precondition, and successor rule |
| green | eligible but untried transition | recorded as available, with deterministic priority/order |
| yellow | transition on the current active search path | predecessor link or stack entry |
| red | transition fully explored and closed | closure reason and no-repeat guard |
| Ariadne/start | initial configuration | immutable run-start record |
| Minotaur/target | stated success configuration | explicit success predicate |
| thread | reconstructable active path | parent pointers, stack, or append-only trace |

The resulting search invariant can be written:

> At every nonterminal step, the active-path record names a simple, ordered sequence of permitted transitions from the fixed initial configuration to the current configuration; no transition marked closed is selected again.

### Why this is appropriate to multi-algo work

McAulay contributes a space of lawful algebraic transformations: multiply in the declared order, apply a named `Va` projection, apply a declared linity, or test a stated invariant. Trakhtenbrot’s labyrinth method contributes the discipline for **searching** through a finite, explicitly bounded subset of those transformations.

For example, a bounded normal-form or proof-search experiment can declare:

```text
configuration = represented multenion expression + current rule position
transition    = one named, legal rewrite or projection
target        = a specified normal form or invariant-satisfying expression
closed        = an already exhausted configuration/transition under this run
bound         = finite rule set, finite expression-size limit, and finite step budget
```

The active trace then shows exactly which legal transformations were tried, which were rejected or exhausted, and how a target was reached—or why the bounded search returned to its start without finding one.

### Termination and failure claims

The labyrinth argument only proves termination when the search space is finite and the no-repeat discipline is actually enforced. Therefore a hybrid search must state at least one finite bound:

- a finite set of configurations;
- a maximum expression size or grade range;
- a maximum search depth/step count; or
- an acyclic, decreasing measure proved to terminate.

If none is available, the correct output is not “no solution.” It is a named limit such as `STEP_BOUND_REACHED`, with the active path and unexplored frontier preserved in the trace.

### Do not force the analogy

An ordinary fixed sequence such as `validate → multiply → project → verify → halt` is not itself a labyrinth search; it needs no backtracking and may be better specified by the simple transition contract above. Use the labyrinth model only when the machine truly encounters a finite set of alternatives and must search, backtrack, or establish that no permitted route to the target remains within the stated bound.

This distinction is important. The value of Trakhtenbrot’s model is not that every controller can be called a labyrinth; it is that a real search controller can inherit a clear invariant, a termination argument, and a reconstructable failure result.

## Three worthwhile first demonstrations

### A. Grade decomposition

**Formal question:** can a represented multenion be separated into declared `Va` components and reconstructed?

**Algorithm:** read a canonical coefficient layout, select each declared grade, store each component, recombine, then compare with the original representation.

**Evidence:** original value, each projected component, reconstructed value, equality check, trace.

**Why it is useful:** it exercises representation, grade projection, storage, and verification without requiring an ambitious geometric claim.

### B. Ordered product and commutation check

**Formal question:** does the implementation preserve `iaib = −ibia` for chosen distinct basis units and `ia² = −1`?

**Algorithm:** select a pair of primitive units, compute both operand orders, negate/compare as specified, then test the square case separately.

**Evidence:** both products in operand order, expected sign/basis result, pass/fail check, trace.

**Why it is useful:** it tests the foundational noncommutativity without pretending that all higher-grade theory is implemented.

### C. A named linity with an invariant

**Formal question:** does one explicitly defined linity preserve its stated relationship?

**Algorithm:** load the linity parameters and a test vector; apply the linity; use the designated scalar-part pairing or reciprocal relation as the check; record the transition.

**Evidence:** inputs, linity identity/version, output, pairing result, expected result, trace.

**Why it is useful:** it makes McAulay’s language of transformations operational while retaining Trakhtenbrot’s distinction between operation and algorithm.

## How Trakhtenbrot constrains the claim

Trakhtenbrot adds four checks that prevent the hybrid from becoming a purely verbal proposal:

1. **Determinacy:** no transition may rely on an unstated choice such as “pick a suitable operation.”
2. **Generality:** state the input class for which the procedure works, rather than showing one curated value.
3. **Termination or continued operation:** name a halt condition, a bounded step count, or an intentional ongoing mode.
4. **Feasibility:** distinguish a procedure that exists in principle from one that fits the target’s memory, time, word size, and available arithmetic.

His undecidability chapters add a separate caution: a finite successful test set cannot establish a universal decision procedure for all possible expressions or programs. The appropriate outcome is a bounded verified controller, not a claim to solve all formal questions.

## How McAulay constrains the claim

McAulay prevents the implementation from becoming an arbitrary state machine decorated with algebraic vocabulary:

1. **Basis and grade are semantic commitments.** A coefficient list is not a multenion until its basis order and grade interpretation are fixed.
2. **Product order is semantic.** Noncommutation must be preserved and tested.
3. **Projection is an operation.** `Va` must have an explicit implementation and result, not be a prose annotation.
4. **Linities have domains and relations.** A named transformation must state its input/output kinds and the identity it preserves.
5. **Invariants need a form.** Scalar-part pairings and reciprocal systems offer concrete candidates for checks.

## Episode-ready thesis

> McAulay gives us a language in which a machine’s objects and transformations can be named with unusual precision: scalar, vector, grade, product, projection, and invariant. Trakhtenbrot supplies the missing temporal discipline: which operation happens next, what condition permits it, what state changes, how failure is named, and what trace remains. The hybrid is not an intelligence claim. It is a method for making a small formal machine answerable.

## Claims to avoid

- “McAulay’s multenions are a program.” They are a formal algebraic framework, not a supplied program-selection algorithm.
- “A controller becomes multenion-based by using eight or sixteen registers.” Representation must preserve declared algebraic operations and identities.
- “A successful output proves the algebra.” It may be a coincidence unless the operation and invariant check are stated.
- “Noncommutativity means nonassociativity.” McAulay’s multiplication is associative.
- “A finite controller realizes the Church–Turing thesis.” It does not.
- “The word-problem results prove a limit of this particular board.” A valid reduction and formal encoding would be required.
